# IT 기술 문서 번역 서비스 PRD

2026-11-04 작성 · 2026-11-12 수정(요약 기능 반영) · 이성헌

## 개요

IT 기술 문서 번역 서비스(가칭)는 영어 개발 문서와 논문을 로컬 LLM으로 한국어로 번역하고, 번역 결과를 요약해 문서 파일(docx, PDF)로 만든 뒤 결과를 DB에 저장하는 웹 서비스다. 번역 전문도 옵션으로 내려받을 수 있다.

- **배경**: 개발을 공부하면 영어 문서를 읽을 일이 많다. 번역, 용어 정리, 요약이 서로 다른 도구에 흩어져 있어 번거롭다.
- **접근**: 외부 API 대신 로컬 LLM을 쓴다. 비용이 들지 않고, 업로드한 문서가 외부로 나가지 않는다.
- **대상**: 영어 문서를 번역하고 문서를 만들어 주는 서비스에서 출발해, 경쟁 서비스와 겹치지 않도록 IT 기술 문서(개발 문서, 논문)로 좁혔다.
- **팀**: 이성헌(백엔드, Spring Boot), 김대희(프론트엔드, React).

## 목표와 성공 지표

첫 목표는 기능 수가 아니라, 번역부터 요약, 문서 생성, DB 저장까지 한 번에 이어지는 흐름을 로컬 환경에서 완성하는 것이다.

| 목표 | 지표 | 기준 |
| --- | --- | --- |
| 핵심 흐름 완성 | 문서 업로드부터 요약본 다운로드까지 | 끝까지 동작 |
| 용어 일관성 | 용어집에 등록한 용어가 번역에 적용된 비율 | 목표치는 팀이 정함 |
| 로컬 구동 | 로컬 LLM이 개발 PC에서 실행되어 번역·요약 | 시연 가능 |
| 실사용 | 직접 써 본 사용자 수와 피드백 | 목표 인원은 팀이 정함 |
| 협업 경험 | 브랜치 → PR → 리뷰 → 머지 | 모든 기능을 PR로 반영 |

## 타깃 사용자와 사용 시나리오

주 사용자는 개발을 공부하면서 영어 개발 문서나 논문을 읽는 학생이다. 팀원 두 명이 가장 먼저 쓰는 사용자가 되고, 주변 학과 사람들로 넓힌다.

1. 영어 개발 문서나 논문 파일을 업로드한다.
2. 필요하면 자주 쓰는 전문 용어와 원하는 번역어를 용어집에 등록한다.
3. 번역을 실행하면 화면에서 문단별 번역 결과와 진행 상태를 확인한다.
4. 요약 길이(짧게, 보통, 길게)를 고르면 번역 결과의 요약본이 만들어진다.
5. 요약본을 문서 파일(docx, PDF)로 내려받는다. 필요하면 번역 전문도 함께 받는다.

## 범위

MVP는 업로드부터 번역, 요약, 문서 생성, DB 저장까지다. 나머지는 핵심 흐름이 동작한 뒤에 추가한다.

| 구분 | 내용 |
| --- | --- |
| MVP 포함 | 회원가입·로그인, 문서 업로드, 로컬 LLM 번역, 용어집, 요약(길이 선택), 요약본 문서 생성, 번역 전문 다운로드(옵션), DB 저장 |
| MVP 이후 | 번역 기록, 용어 후보 추천, 단어장 연동 |
| 제외 | 외부 번역 API, 원본 서식의 완전한 유지, 스캔 문서(OCR), 모바일 앱 |

## 기능 요구사항

우선순위는 Must(MVP 필수), Should(MVP 직후), Could(여유가 있을 때) 순이다. 지원할 입력 파일 형식은 텍스트 중심 형식(txt, md)부터 시작한다.

| ID | 기능 | 동작 | 우선순위 |
| --- | --- | --- | --- |
| F1 | 회원가입·로그인 | 사용자별로 문서와 용어집을 분리해 저장한다. | Must |
| F2 | 문서 업로드 | 영어 문서 파일을 올리고 텍스트를 추출해 문단(Segment)으로 나눈다. | Must |
| F3 | 로컬 LLM 번역 | 문단 단위로 로컬 LLM에 보내 영어에서 한국어로 번역한다. 실패한 문단만 다시 실행할 수 있다. | Must |
| F4 | 용어집 | 용어와 번역어를 등록·수정·삭제하고, 번역할 때 적용한다. | Must |
| F5 | 요약 | 번역된 문서를 사용자가 고른 길이(SHORT, MEDIUM, LONG)로 요약한다. 다시 요약하면 덮어쓴다. | Must |
| F6 | 결과 파일 생성 | 요약본을 docx, PDF로 만들어 내려받는다. 옵션으로 번역 전문(md, txt, docx)도 받는다. | Must |
| F7 | DB 저장 | 번역·요약 결과를 Segment와 Document에 저장한다. | Must |
| F8 | 번역 기록 | 이전에 번역한 문서 목록을 다시 본다. | Should |
| F9 | 용어 후보 추천 | 문서에서 전문 용어 후보를 뽑아 용어집에 추가하도록 제안한다. | Should |
| F10 | 단어장 연동 | 용어집의 용어를 퀴즈로 복습한다. 앞서 기획한 단어장 아이디어를 이어받는다. | Could |

## 처리 흐름

```
업로드·분할 → 로컬 LLM 번역 → 요약(길이 선택) → 문서 파일 생성 → DB 저장
                 ↑      ↓ 실패
                 └ 문단 재요청 (실패한 문단만)
```

문서를 문단 단위로 나눠 번역하고, 번역이 실패한 문단은 그 문단만 다시 요청한다. 번역이 끝난 문서는 사용자가 길이를 골라 요약하고, 요약본(또는 번역 전문)을 문서 파일로 만든다. 번역과 요약 결과는 DB에 저장한다.

## 데이터 모델

엔티티는 네 개로 시작한다. 필드는 초안이고, 팀이 협의해 확정한다. `user`는 일부 DB에서 예약어라 Member로 한다.

| 엔티티 | 주요 필드 | 비고 |
| --- | --- | --- |
| Member | id, email, password(해시), nickname, createdAt | email은 유니크 |
| Document | id, member(FK), title, originalFilename, fileType, filePath, resultFilePath, status, summaryStatus, summaryLength, summary, createdAt | status: UPLOADED, TRANSLATING, DONE, FAILED. summaryStatus: NONE, SUMMARIZING, DONE, FAILED. 파일 자체는 DB가 아니라 저장소에 두고 경로만 저장한다. |
| Segment | id, document(FK), seq, sourceText, translatedText, status | 문단 단위. seq로 순서를 유지하고, 실패한 문단만 재실행한다. status: PENDING, DONE, FAILED |
| Term | id, member(FK), sourceTerm, targetTerm, note, createdAt | (member, sourceTerm)에 유니크 제약. F10 때 wrongCount, nextReviewDate를 추가한다. |

관계는 Member 1 : N Document, Document 1 : N Segment, Member 1 : N Term이다.

## 기술 스택

백엔드는 Spring Boot로 만들고, 번역과 요약은 외부 API 없이 로컬 LLM으로 처리한다.

| 구분 | 선택 | 비고 |
| --- | --- | --- |
| 백엔드 | Spring Boot, Spring Data JPA | REST API |
| DB | MySQL | 초기 개발은 H2 |
| 번역·요약 엔진 | 로컬 LLM | 모델은 미정. 같은 문서로 2~3개를 비교해 선정한다. 개발 PC는 CPU로 구동하므로 작은 모델부터 비교한다. |
| 모델 서빙 | Ollama 등 (후보) | Spring Boot가 localhost HTTP로 호출한다. `Translator`, `Summarizer` 인터페이스 뒤에 두어 교체할 수 있게 한다. |
| 문서 처리 | Apache POI(docx) 사용, PDF는 PDFBox 등 (후보) | PDF는 한글 폰트를 직접 넣어야 한다. |
| 프론트 | React | 김대희 담당 |
| 협업 | Git, GitHub | 브랜치 → PR → 리뷰 → 머지 |

## 비기능 요구사항과 협업 규칙

- **보안·개인정보**: 비밀번호는 해시(BCrypt)로 저장하고, 사용자는 자기가 올린 문서와 용어집만 조회한다. 로컬 LLM을 쓰므로 문서가 외부로 나가지 않는다.
- **성능**: 번역과 요약은 오래 걸리므로 요청과 결과 조회를 분리하고(202 응답, 상태 조회), 상태 값으로 진행을 보여 준다.
- **하드웨어**: 모델 크기는 개발 PC의 메모리와 GPU에 맞춰 정한다. 현재 개발 PC는 전용 GPU가 없어 CPU로 구동한다.
- **협업**: `main`에는 직접 푸시하지 않는다. 기능마다 브랜치를 만들고 PR을 올려 상대가 리뷰한 뒤 머지한다.

역할 분담:

| 담당 | 역할 |
| --- | --- |
| 김대희 | 프론트엔드(React): 업로드·번역 진행 화면, 문단별 결과 화면, 요약 길이 선택, 용어집 화면, 다운로드 옵션(요약본/번역 전문) |
| 이성헌 | 백엔드: 문서 처리, 로컬 LLM 연동, 용어집, 요약, DB, 인증 |

API 명세(`docs/API.md`)를 기준으로 프론트와 백엔드가 서로 기다리지 않게 한다.

## 마일스톤

한 번에 다 넣지 않고 단계별로 끝내며 넘어간다. 날짜는 교수님 일정을 확인한 뒤 채운다.

1. **기획 확정**: PRD, 역할 분담, API 명세, 교수님 확인.
2. **번역 핵심**: 업로드, 문단 분할, 번역(가짜 번역기), 용어집, DB 저장 (F2, F3, F4, F7). 완료.
3. **요약과 문서 생성**: 요약(길이 선택), 요약본 docx 출력, 번역 전문 옵션 (F5, F6). 진행 중.
4. **로컬 LLM 연결**: 모델 설치, 모델 2~3개 비교, `Translator`·`Summarizer` 구현체 교체.
5. **서비스 완성**: 회원, 번역 기록, PDF 출력 (F1, F8), 프론트 연동, 시연과 피드백.
6. **확장**: 용어 후보 추천, 단어장 연동 (F9, F10).

## 리스크와 미결정 사항

| 리스크 | 대응 |
| --- | --- |
| 개발 PC 사양이 부족해 모델이 느리거나 실행되지 않음 | 모델을 고르기 전에 메모리와 GPU를 확인하고, 작은 모델부터 비교한다. |
| 로컬 LLM의 번역 품질이 낮음 | 용어집을 반영하고, 문단 단위로 나눠 번역하며, 결과를 사용자가 수정할 수 있게 한다. |
| 긴 문서의 요약이 느리거나 품질이 낮음 | 문단별로 요약한 뒤 합치는 방식으로 나눠 처리하고, 요약 길이를 사용자가 고르게 한다. |
| LLM이 정해진 출력 형식을 어김 | 출력을 검증하고, 실패하면 해당 문단만 다시 요청한다. |
| 무료 호스팅에서는 모델을 돌릴 수 없어 외부 배포가 어려움 | 모델이 돌아가는 PC에서 시연하고 주변 사용자에게 써 보게 하는 것을 목표로 한다. |
| PDF에서 한글이 깨짐 | 한글 폰트를 직접 포함해 만들고, docx를 먼저 완성한다. |
| 원본 서식을 그대로 유지하기 어려움 | 텍스트 중심 형식부터 지원하고, 서식 유지는 이후 목표로 둔다. |
| 기능을 너무 많이 넣어 완성하지 못함 | Must 기능만 먼저 완성한다. |
